# Плагины Pixso

Pixso повторяет Figma Plugin API, но не совпадает с ним в деталях, а разные
сборки клиента ведут себя по-разному. Здесь не пересказ документации, а список
мест, где плагин ломается молча, и способов не ломаться.

Где проверено: корпоративный стенд с клиентом 2.3.0 работает полностью.
Pixso Desktop 2.2.7 для macOS не передаёт сообщения из окна в плагин и не
отдаёт файл окна, обходы ниже рассчитаны и на него. Если у вас 2.2.7,
обновитесь.

Главное, что стоит понять сразу: **плагин живёт в двух изолированных половинах.**

| | Где | Что есть | Чего нет |
|---|---|---|---|
| `main.js` | песочница главного потока | доступ к документу, узлам, `exportAsync`, `clientStorage` | DOM, сеть, `Blob`, `URL`, любые Web API |
| `ui.html` | iframe с origin `null` | весь браузер: DOM, canvas, `Blob`, `CompressionStream`, скачивание | доступ к документу Pixso |

Значит любая работа делится так: **данные собирает `main.js`, файлы и картинки
делает `ui.html`**, а между ними ходит `postMessage`. Этот канал и есть главный
источник боли, поэтому у него отдельная страница `references/messaging.md`.

## С чего начать

**Новый плагин** не пиши с нуля, возьми рабочий каркас:

```bash
cp -r <путь-к-скиллу>/assets/scaffold/. <папка-проекта>/
```

В каркасе собраны обходы из ловушек ниже: проверенный манифест из шести полей
(без `menu`), двойная подписка на сообщения и их нумерация, рукопожатие
с повторами, хранилище под таймером, честные состояния окна, мок и два прогона
без Pixso, дев-сервер, сборка с окном, вшитым в код, и `pack.sh` с проверкой
архива. Дальше меняй `manifest.json` (имя, id) и наполняй `main.js` и `ui.html`
своей задачей.

Каркас собран по образцу плагинов, которые работают на стенде, но сам на стенде
не запускался. Первая проверка нового плагина на стенде всё равно обязательна.

**Существующий плагин** начинай с `manifest.json` и того, как устроен обмен
сообщениями, а потом сверься со списком ловушек ниже: большинство случаев
«оно не работает» это один из этих пунктов, а не ошибка в логике. Таблица
«что видно, почему, как проверить» лежит в начале `references/pitfalls.md`.

## Ловушки, которые стоят дня отладки

Порядок по тому, как часто попадаются. Подробный разбор с датами проверок
в `references/pitfalls.md`, номера граблей там свои.

**1. «Плагин не запускается»: сначала смотри на архив, потом на манифест.**
Симптом один на две причины: карточка есть, нажатие не открывает ничего, ни окна,
ни ошибки, и в консоли **ни одной строки**, потому что до кода дело не доходит.
Отладка кода здесь бесполезна, код не запускался.

*Причина первая, подтверждённая публикацией 08.09.2026: раскладка архива.*
Клиент ищет в пакете запись с именем **ровно `manifest.json` в корне архива**,
следом `main` и `ui` по путям из манифеста, тоже точным совпадением. Папку-обёртку
он не срезает, а ошибку разбора **глотает молча**. Архив, сжатый через Finder на
macOS, содержит саму папку (`имя-папки/manifest.json`) плюс `__MACOSX`
и `.DS_Store` и не запускается. Три круга публикации ушло на то, чтобы это
найти, плоский архив заработал с первого раза.

Локальная загрузка идёт **мимо архива**: файлы читаются с диска по путям
манифеста. Отсюда правило: **«локально работает, на публикации нет» при одинаковом
коде значит упаковку или сервер, а не плагин.** Проверяется одной командой,
первой записью обязан идти `manifest.json`:

```bash
unzip -l пакет.zip | head
```

*Причина вторая: манифест.* Набор, проверенный запуском на стенде 01.09.2026:

```json
{
  "id": "pptx_export",
  "name": "Экспорт в PowerPoint",
  "main": "dist/main.js",
  "ui": "dist/ui.html",
  "permissions": ["activeDocument", "currentPage", "currentSelection"],
  "editorType": ["pixso", "dev"]
}
```

- `editorType` описан в документации манифеста, но его нет в типах
  `@pixso/plugin-typings`. Без него плагин виден только в режиме дизайна;
- `permissions` именно с этими именами, их нет ни в документации, ни в типах;
- `menu` не нужен, метаданные (`version`, `author`, `description`, `icon`,
  `type`, `manifestVersion`, `host`) тоже.

**Правило: манифест берётся из проверенного образца и не додумывается.**
В чужих плагинах встречаются другие наборы полей, копировать их не нужно.
Клиенту для запуска хватает `name` и `main`, так что если манифест уже такой,
как выше, а плагин не запускается, **виноват не он**: смотри архив. Сборщик
каркаса сверяет набор полей на точное совпадение, подробности
в `references/publishing.md`.

**2. Канал «окно → плагин» может молчать.** Сообщения из `main.js` вниз доходят,
а обратно ни одного. Зависит от сборки клиента. Отсюда правила: подписывайся на
сообщения **всеми способами сразу** (`ui.onmessage` и `ui.on('message')`, до
и после `showUI`), а окно не считай источником истины: `main.js` сам присылает
стартовые данные, не дожидаясь «я готово». Подробности и код
в `references/messaging.md`.

**3. Одно нажатие выполняется несколько раз.** Окно шлёт сообщение нескольким
адресатам, `main.js` подписан двумя способами, и дубли приходят с задержкой,
флаг «занят» их не ловит. Нумеруй сообщения в окне и в `main.js` обрабатывай
только первое с этим номером. Код в `references/messaging.md`, раздел
«Дедупликация».

**4. `localStorage` в окне бросает `SecurityError`.** Origin у iframe `null`,
хранилище недоступно. Настройки живут в `pixso.clientStorage` (это в `main.js`),
окно просит их сообщением. `clientStorage` может не ответить вовсе, поэтому
ожидание под таймером. Перед `closePlugin()` дай записи дописаться (`setTimeout`
около 400 мс), иначе она потеряется.

**5. Файл окна из манифеста может не доехать.** Код запускается, окно открывается
пустым. Лечится тем, что разметка вшивается прямо в скрипт. **Поле `ui` при этом
остаётся в манифесте, а файл в пакете**, иначе набор полей разойдётся
с проверенным. Сборка `tools/make-local-build.js` в каркасе делает это сама.

**6. Свойства узлов надо читать через обёртку.** В разных сборках часть свойств
отсутствует, и обращение бросает исключение, а не отдаёт `undefined`:

```js
function prop(node, name) {
  try { return node[name]; } catch (e) { return undefined; }
}
```

**7. Фигмовские имена свойств принимаются и молча не работают.** У автолейаута
в Pixso два набора имён, и работает родной: `stackMode`, `stackSpacing`,
`stackChildCounterSizing`, `autoLayoutAbsolutePos` и другие. Ставь оба и проверяй
по фактическому размеру, «не бросило» ещё не значит «применилось». `resize()`
молча выключает режим «по содержимому» по обеим осям. Таблица имён
в `references/pitfalls.md`, грабля 7.

**8. Текст не создаётся без загруженного шрифта,** а на стенде нужного шрифта
может не быть. Перед `characters` вызывай `loadFontAsync` с перебором: свой шрифт,
шрифт из этого же макета, системный. Остальные грабли записи в чужой документ
(экземпляры компонентов, автолейауты, повторный запуск) в `references/pixso-api.md`,
раздел «Создание и правка узлов».

### Ещё коротко, подробно в `references/pitfalls.md`

- **Мастеров библиотечных компонентов в дереве страниц нет.** Обход страниц их
  не находит. Иди от экземпляров: `instance.mainComponent`.
- **`findAll` не заходит внутрь экземпляра.** Обходи детей сам или пиши текст
  через свойство компонента (`setProperties`).
- **`getStyledTextSegments` заглушка**, всегда отдаёт пустой список. Стиль куска
  текста дают `getRangeFillStyleId` и `getRangeTextStyleId`.
- **`exportAsync` не применяет прозрачность слоя** и у неотсечённого фрейма
  отдаёт картинку больше фрейма. Прозрачность переноси сам, `clipsContent`
  включай на время съёмки и возвращай в `finally`.
- **Слой с режимом наложения или размытием фона** нельзя снять отдельно: его цвет
  зависит от того, что под ним.
- **Каталог библиотеки отдаёт стили общим списком**, а не в виде из типингов.
  Кто читает только вид из типингов, получает пустой каталог без ошибки.
- **Обновления библиотек плагин видит, но обновить может только все сразу.**
  Ключ компонента живёт одну публикацию, вшивать ключи нельзя, ищи по именам.
- **Скачивание файла из окна может быть запрещено стендом.** Автоскачивание
  пробуй, но всегда оставляй видимую кнопку.

## Рабочий цикл

Большую часть работы можно делать **вообще без Pixso**, и это быстрее:

- `tools/mock-ui.html` открывает `ui.html` в iframe и притворяется песочницей:
  отдаёт список узлов, миниатюры, прогресс. Проверяет весь интерфейс и его
  состояния, переключатели в адресе (`?frames=0`, `?run=1`);
- `tools/harness.js` прогоняет код из `ui.html` в Node с заглушками DOM;
- `tools/main-harness.js` прогоняет `main.js` с подставным документом Pixso:
  порядок кадров, дедупликацию, молчащее хранилище, свою работу.

Отладка в самом Pixso без перезагрузки приложения на каждую правку:

```bash
node tools/dev-server.js       # порт 5201 зашит в Pixso, менять нельзя
```

Дальше в Pixso: панель плагинов, режим разработки. Сервер отдаёт `ui.html` по
HTTP и шлёт `manifest`, `main` и `ui` в WebSocket на `/plugin`. Правка файла
означает перезагрузку на стороне Pixso. В этом режиме у окна настоящий origin,
поэтому скачивание и хранилище перепроверяй на собранном плагине.

Как устроены мок и прогоны и как их расширять, в `references/testing.md`.
Заводи их сразу, а не «когда понадобится»: без них каждая проверка стоит
перезапуска приложения и ручного клика по холсту.

## Правила, которые экономят время

**Ноль зависимостей.** Плагин это три текстовых файла, npm, сборщики и внешние
реестры в закрытом контуре недоступны. Значит zip, XML, WebSocket собираются
руками. Это платится один раз, а плагин остаётся переносимым. Сжатие берётся
у браузера: `CompressionStream('deflate-raw')` в окне, а если его нет, данные
кладутся без сжатия.

**Сначала измерить, потом чинить.** Если непонятно, почему не работает, плагин
должен сам показать в окне цифры и причины: какие каналы сработали, что пришло,
что не встало. На угадывании уходят дни, на диагностике один заход.

**Отчёт вместо тишины.** Плагин работает с чужими макетами, и часть узлов
неизбежно не переносится один в один. Сделай журнал, который пишет по каждому
объекту, что получилось, что осталось приблизительным и почему. Это и диагностика
для автора, и объяснение для пользователя.

**Состояния не должны врать.** Пустой список, «ничего не выбрано», отвалившийся
канал, заблокированное скачивание: у каждого свой честный экран. Кнопка, которая
ничего не делает, хуже отсутствующей кнопки.

## Интерфейс окна

Рекомендуем верстать окно по **DAIS**, UI kit дизайн-системы FinAI на токенах
SDDS FinAI: так окна плагинов разных авторов выглядят одинаково. Каркас уже
в этих цветах. Если у команды своя дизайн-система, подставьте её токены
в переменные в начале `ui.html`, разметку трогать не придётся.

Перед вёрсткой окна читай `references/ui-dais.md`: где смотреть компоненты,
готовые значения токенов, контролы, иконки, тексты. Компоненты DAIS написаны
на React, а окно плагина без npm, поэтому из DAIS берутся цвета, размеры и вид,
а вёрстка своя.

Общее правило, независимое от дизайн-системы: окно плагина это маленькая
панель, а не сайт. Один экран, минимум настроек, техническое спрятано за
кнопкой. То, что составляет суть плагина, в настройки не выводится вовсе.

## Упаковка и публикация

```bash
node tools/make-local-build.js   # local-build/ для своей машины, release/ для репозитория
./pack.sh                        # publish/<id>.zip из release/, с проверками
```

`pack.sh` собирает пакет, прогоняет обе проверки и в конце читает архив так же,
как его читает клиент: `manifest.json` первой записью, без `__MACOSX`
и `.DS_Store`, пути из манифеста находятся.

**Собирать архив мышкой нельзя.** «Сжать» в Finder добавляет папку-обёртку
и служебные файлы macOS, и опубликованный плагин не запускается, см. ловушку 1.

Если плагин проверяют на стенде без терминала, его берут готовым из репозитория.
Поэтому `release/` пересобирается перед каждым коммитом и коммитится вместе
с кодом, а коммит сразу отправляется в удалённый репозиторий.

Для карточки плагина нужны обложка 1600×900, иконка 128×128 и текст описания.
Подробности в `references/publishing.md`.
