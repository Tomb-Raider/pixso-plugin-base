# Грабли Pixso с датами проверок

Всё, что выяснено опытом на Pixso Desktop 2.2.7 для macOS (личная машина для
проверки) и на корпоративном стенде с клиентом 2.3.0. Документация Pixso местами
расходится с поведением приложения, здесь описано поведение. Читать перед началом
любого нового плагина: каждый пункт стоил дня отладки.

Номера граблей здесь свои, они не совпадают с номерами ловушек в `SKILL.md`.

---

## Устройство плагина

Три файла, больше ничего не нужно:

| Файл | Где выполняется | Что можно |
|---|---|---|
| `manifest.json` | нет | описание плагина |
| `main.js` | песочница основного потока | доступ к документу; нет DOM, сети, файлов |
| `ui.html` | `<iframe>` с пустым origin | весь Web API; нет доступа к документу |

Между собой общаются сообщениями: `pixso.ui.postMessage` вниз,
`parent.postMessage({ pluginMessage }, '*')` наверх.

Манифест берётся из проверенного образца из шести полей, подробно в разделе
«Манифест» ниже и в `publishing.md`.

## Если что-то не работает

Что видно, что обычно сломалось и как это проверить. Подробности в разделах ниже

| Что видно | Почему | Как проверить и что делать |
|---|---|---|
| Карточка плагина есть, нажатие ничего не делает, в консоли пусто | Архив с папкой-обёрткой или мусором macOS | `unzip -l пакет.zip`: первой записью должен идти `manifest.json`. Собирать только `pack.sh`, раздел «Архив» |
| То же самое, а архив правильный | Набор полей манифеста не совпадает с проверенным | Сравнить с образцом из шести полей, раздел «Манифест» |
| То же самое, а манифест правильный | Путь в манифесте ведёт на файл, которого нет | Пути считаются от папки манифеста, грабля 2 |
| Локально работает, после публикации нет | Упаковка или сервер, код тут ни при чём | Сначала архив, потом манифест |
| Окно белое, а код работает (`pixso.notify()` до `showUI` срабатывает) | Файл из `manifest.ui` пришёл пустым | Вшить разметку в скрипт, грабля 1 |
| Кнопки в окне не отвечают, а данные из плагина в окно приходят | Канал «окно → плагин» не работает в этой сборке клиента | Проверить версию Pixso. Обработчик двумя способами, генерация в `main.js`, грабля 3 |
| Одно нажатие срабатывает два-пять раз | Сообщение доезжает по нескольким каналам | Нумеровать сообщения, грабля 3 |
| Окно висит на загрузке | `clientStorage` не ответил | Ожидание под таймером, грабля 4 |
| Консоль отвечает «нет плагина для отладки» | Консоль обслуживает только режим разработки | Диагностику показывать в окне плагина, грабля 5 |
| Плагин не видит компоненты библиотеки на страницах | Мастеров библиотеки в дереве страниц нет | Идти от экземпляров через `mainComponent`, грабля 6 |
| Свойство автолейаута записалось без ошибки, а слой не тянется | Фигмовское имя свойства не применяется | Ставить родное `stack*` и проверять по размеру, грабля 7 |
| Текст внутри экземпляра не находится или не меняется | `findAll` не заходит внутрь экземпляра | Обходить детей самому или писать через свойство компонента, грабля 8 |
| В снимке слой непрозрачный | `exportAsync` не применяет прозрачность слоя | Переносить прозрачность вручную, грабля 9 |
| Каталог библиотеки пустой, ошибки нет | Читали только вид из типингов | Читать оба вида, грабля 12 |

Что проверено и **не влияет**: ведущая точка в путях манифеста (`./main.js` и `main.js` равнозначны),
параметры `showUI` (`width`, `height`, `title`). Если так же ломается и официальный пример Pixso,
собранный их же инструментом, дело в клиенте или упаковке, а не в коде плагина

## Архив: `manifest.json` обязан лежать в корне

**Первое, что проверяем, когда опубликованный плагин не запускается.**
Подтверждено публикацией 08.09.2026: плагин три круга не работал на стенде,
пересобрали архив плоским, и он заработал сразу. Код и манифест при этом
не меняли.

Клиент скачивает пакет и ищет в нём запись с именем **ровно `manifest.json`,
в корне архива**; следом ищет `main` и `ui` по путям из манифеста, точным
совпадением (ведущее `./` он срезает). Папку-обёртку не срезает, а ошибку
разбора **глотает молча**: снаружи это карточка, которая есть, и нажатие,
которое ничего не делает.

Архив из Finder («Сжать» в контекстном меню) выглядит так и **не работает**:

```
пакет/                     ← папка-обёртка, из-за неё всё и ломается
пакет/manifest.json
пакет/dist/main.js
__MACOSX/…  и .DS_Store    ← служебный мусор macOS
```

А так работает:

```
manifest.json
dist/main.js
dist/ui.html
```

**Локальная загрузка идёт мимо архива**: файлы читаются с диска. Отсюда
правило распознавания: **«локально работает, на публикации нет» при
одинаковом коде это упаковка или сервер, а не плагин.**

Собирает архив только `pack.sh`; он же после упаковки читает результат так
же, как его читает Pixso, и падает, если `manifest.json` не первой записью,
внутри мусор macOS или пути из манифеста не находятся. Проверить руками:

```bash
unzip -l пакет.zip | head
```

## Манифест: держаться проверенного образца

**Шесть полей, проверено запуском на внутреннем стенде 01.09.2026:**

```json
{
  "id": "pptx_export",
  "name": "Экспорт в PowerPoint",
  "main": "dist/main.js",
  "ui": "dist/ui.html",
  "permissions": ["activeDocument", "currentPage", "currentSelection"],
  "editorType": ["pixso", "dev"]
}
```

- `editorType` и `menu` описаны в документации манифеста, но их нет в типах
  `@pixso/plugin-typings`. Без `editorType` плагин виден только в режиме дизайна.
- `permissions` нет ни в документации, ни в типах, этот набор взят из манифеста
  плагина, который уже запускался на стенде.
- `menu` не нужен: с этим набором плагин открывается нажатием на карточку.
- По поведению клиента для запуска хватает `name` и `main`. До 08.09.2026
  плагины не запускались из-за архива (раздел выше), и тогда же перебирались
  наборы полей, поэтому какой набор был ни при чём, уже не узнать. Шесть полей
  выше с тех пор не подводили, держитесь их и не додумывайте.

Симптом неправильного манифеста тот же, что у битого архива: **карточка плагина
есть, нажатие не делает ничего, в консоли ни одной строки.** Архив встречается
чаще, проверяйте сначала его.

Сборщик (`tools/make-local-build.js` в каркасе) сверяет набор полей **точно**
и падает не только на нехватке, но и на любом добавлении: новое поле означает
новый круг публикации, и решение принимается осознанно, а не по недосмотру.

## Грабли, на которые мы наступили

### 1. Файл из `manifest.ui` доезжает пустым

При локальной загрузке плагина `__html__` приходит **нулевой длины**. Окно
открывается белым, хотя код запускается: `pixso.notify()` до `showUI()`
срабатывает.

**Решение:** вшивать разметку прямо в скрипт. Тогда читается один файл:
тот, который читается нормально.

Поле `ui` при этом **остаётся в манифесте, а файл в пакете**: набор полей
обязан совпадать с проверенным образцом (см. раздел про манифест), а лишний
файл ничему не мешает. Раньше здесь было написано «убрать `ui` из манифеста,
поле необязательное». При локальной загрузке это правда, на публикации
плагин с урезанным набором полей не запускается.

```js
var UI_HTML = (typeof INLINE_UI === 'string' && INLINE_UI.length)
  ? INLINE_UI
  : ((typeof __html__ === 'string') ? __html__ : '');
pixso.showUI(UI_HTML);
```

Сборка `tools/make-local-build.js` делает это автоматически.

### 2. Пути в манифесте считаются от папки самого манифеста

Ведущая точка роли не играет: `./main.js` и `main.js` равнозначны. Собранный
официальным инструментом плагин кладёт код в `dist/`, и в пакете надёжнее
делать так же:

```
manifest.json
dist/main.js
dist/ui.html
```

**Но у манифестов две роли, и путать их нельзя.** Манифест в корне репозитория
загружают локально прямо оттуда: рядом с ним лежат `main.js` и `ui.html`,
и ссылаться он должен на них. Манифест в пакете (`release/`, `local-build/`)
ссылается на `dist/`. Пути проставляет сборка, набор полей у обоих один и тот же.

Если манифест ссылается на файл, которого нет, Pixso **молча не запускает
плагин**: загрузка проходит, карточка появляется, нажатие не делает ничего.
Симптом неотличим от неправильного набора полей, а причина другая. Мы на это
наступили 04.09.2026: корневой манифест переписали на `dist/`, папки `dist/`
в корне нет, и плагин перестал запускаться. Поэтому `make-local-build.js`
теперь проверяет **и** набор полей, **и** что оба пути ведут на существующие
файлы (в исходном манифесте и в каждом собранном пакете).

### 3. Канал «окно → плагин» работает не во всех сборках

Бывает, что песочница жива (пульс из `main.js` в окно идёт), а ни одна команда
из окна не доходит: ни в `parent`, ни в `top`, ни с `pluginId`, ни без него.
Воспроизводится на официальном примере Pixso, собранном их же инструментом,
то есть дело не в коде плагина.

**Это зависит от версии клиента Pixso, а не от плагина.** Проверено прямым
сравнением одного и того же плагина:

| Где | Клиент | Результат |
|---|---|---|
| Pixso Desktop на личной машине, macOS | **2.2.7** | пустой `ui`-файл, кнопки в окне мертвы, консоль не видит плагин |
| Корпоративный стенд | **2.3.0** | работает полностью, включая кнопки |

Похоже, в 2.2.7 локально загруженный плагин регистрируется не до конца, и все
три поломки от этого. Если столкнулись, первым делом проверьте версию клиента
и обновитесь.

Практический вывод: **разрабатывать на «плохой» машине выгодно.** Если работает
там, где связь рвётся, на нормальной сборке заработает тем более. Обходы
ниже безвредны для исправной среды.

**Что помогает:**

- **не полагаться на канал из окна для того, что можно сделать самому.**
  Вся работа (генерация, разбор документа, сборка данных) живёт в `main.js`;
  окно только показывает и просит. Направление «плагин → окно» не подводило
  ни разу, поэтому стартовые данные плагин присылает сам, не дожидаясь
  просьбы;
- **вешать обработчик всеми способами сразу**: присваиванием `ui.onmessage`
  и подпиской `ui.on('message')`, до `showUI` и после. Присваивание может
  «прижиться» (свойство читается обратно), но ничего не доставлять;
- **не ждать сигнала готовности от окна.** Отправлять стартовые данные самому,
  несколько раз в первые секунды.

**Одно нажатие доезжает несколько раз, и флаг «занят» не спасает.** Окно шлёт
наверх нескольким адресатам (`parent`, `top`), а `main.js` подписан двумя
способами, до `showUI` и после. Дубли приходят **не синхронно**: пока первый
обрабатывается, второй ещё в пути. Если работа быстрая (например, компоненты
уже в кэше), к приходу дубля флаг `busy` успевает сброситься, и действие
выполняется столько раз, сколько было доставок. На плагине сборки таблиц это
выглядело как пять таблиц на холсте от одного нажатия.

Лечение: нумеровать сообщения в окне и считать обработанным первое.

```js
var seenIds = {}, seenOrder = [];
function alreadyHandled(msg) {
  var id = msg && msg.__id;
  if (id === undefined || id === null) { return false; }
  if (seenIds[id]) { return true; }
  seenIds[id] = 1;
  seenOrder.push(id);
  if (seenOrder.length > 200) { delete seenIds[seenOrder.shift()]; }
  return false;
}
```

Для сообщений без номера (нештатный источник) полезен второй заслон: тот же
набор настроек, пришедший в пределах двух секунд, считать повтором. Осознанные
нажатия при этом глушить нельзя: у них номер есть, и он другой.

**Проверять это надо разнесённой во времени доставкой.** Прогон, который
рассылает дубли синхронно, проходит и без дедупликации: первый вызов ставит
`busy`, остальные отсекаются. Баг ловится только когда дубли идут с задержкой.

### 4. `clientStorage` может не ответить никогда

Запрос настроек иногда не возвращается вовсе. Если на нём построена цепочка
запуска, интерфейс молча висит. Ограничивайте ожидание таймером и отдавайте
данные в окно, не дожидаясь настроек.

`localStorage` в окне недоступен: origin пустой, обращение бросает
`SecurityError`. Постоянные данные только в `pixso.clientStorage`.

### 5. Встроенная консоль плагинов бесполезна для локальных

На локально загруженный плагин отвечает «нет плагина для отладки»: она
обслуживает только режим разработки. Диагностику приходится встраивать в само
окно; на своей машине помогает приёмник отчётов на `localhost:5201`.

### 6. Мастеров библиотечных компонентов в дереве страниц нет

Обход страниц (`page.findAll(n => n.type === 'SYMBOL' || n.type === 'COMPONENT')`)
библиотечные компоненты **не находит**: ни подключённые, ни даже те, что уже
стоят в файле экземплярами. Проверено на внутреннем стенде 07.09.2026: компоненты вытащили в
файл, а плагин видел ноль мастеров.

**Рабочий путь от экземпляров:** обойти узлы, у каждого `INSTANCE` взять
`node.mainComponent` (в части сборок `masterComponent`). Так работает
плагин поиска по библиотекам, и там это не подводило.

Тонкости, которые идут в комплекте:

- **Имя набора у мастера может быть недоступно**: `master.parent` пустой, а сам
  мастер зовётся «Type=Default». Имя набора тогда берётся из имени экземпляра:
  Pixso по умолчанию называет экземпляр именем набора.
- **Внутрь экземпляров спускаться не надо**: там техническая начинка компонента,
  она только шумит. Свой обход стеком с остановкой на `INSTANCE` и быстрее, и
  точнее `findAll`.
- **Страницы перед обходом надо загрузить**: `loadAllPagesAsync()`, а если его
  нет, `page.loadAsync()` у каждой. Иначе невыделенные страницы отдают пустоту
  или бросают.
- **Выделение доступно всегда.** Если обход страниц ничего не дал, дизайнер
  может просто выделить нужные слои: по ним мастера достаются надёжно.
- Библиотеку мастера даёт `master.getLibraryInfoAsync()` → `{ key, name }`;
  вызов небыстрый и умеет не отвечать, поэтому спрашивать стоит один раз на
  набор и под таймаутом.

**Ключ компонента живёт одну публикацию.** Одна и та же библиотека, перенесённая
из боевой среды на стенд и опубликованная заново, отдаёт компоненты с другими
`componentKey`. Значит вшивать ключи в плагин нельзя, искать надо по именам.

**Обратная сторона: через `mainComponent` достаются мастера, которых на
страницах нет.** Экземпляр библиотечного компонента тянет в файл копию
мастера, и лежит она на скрытом служебном холсте (Internal Only Canvas):
обход страниц её не видит, а `instance.mainComponent` отдаёт. Плагинам про
библиотеки (поиск, обновление) это и нужно. Плагину, который правит **свои**
мастера, это вредно: плагин описаний вариантов на странице с одними макетами
показывали наборы, которых в файле «гарантированно нет» (16.09.2026);
в моке такой набор получал и запись описания. Лечение: экземпляры пропускать
целиком, а компоненты с `remote === true` (поле `PublishableMixin` в типах
2.0.4) не брать. Поведение `remote` на стенде отдельно не проверялось.

### 7. Автолейаут: свойство принимается и молча не работает

Проверено на внутреннем стенде 08.09.2026 при сборке таблицы из компонентов.

- **У свойств автолейаута в Pixso ДВА имени, и работает родное.** Фигмовские
  имена (`layoutSizingHorizontal = 'FILL'`, `layoutAlign = 'STRETCH'`)
  записываются без ошибки и не применяются. Ребёнок остаётся своей ширины:
  ячейка 208 в колонке 300, колонки с зазорами. В самом документе те же режимы
  зовутся иначе, и это видно читалкой `.pix` (см. `tools/pix-reader`). У
  растянутого слоя в файле стоит:

  | Смысл | Родное имя | Значение |
  |---|---|---|
  | направление | `stackMode` | `VERTICAL` / `HORIZONTAL` |
  | зазор, отступы | `stackSpacing`, `stackPadding{Top,Right,Bottom,Left}` | числа |
  | размер кадра | `stackPrimarySizing`, `stackCounterSizing` | `FIXED` / `RESIZE_TO_FIT` |
  | **растянуть ребёнка** | `stackChildCounterSizing` | **`RESIZE_TO_FIT`** |
  | занять остаток | `stackChildPrimarySizing` | `RESIZE_TO_FIT` |
  | выравнивание | `stackPrimaryAlignItems`, `stackCounterAlignItems` | `MIN` / `CENTER` / `MAX` |
  | абсолютное положение | `autoLayoutAbsolutePos` | `true` |

  Ставьте оба набора и проверяйте **по фактическому размеру**: «не бросило» и
  даже «читается обратно» ещё не значит «применилось». Размер числом
  (`resize`) это последний эшелон.
- **`resize()` выключает «по содержимому», сразу по ОБЕИМ осям и молча**
  (сборщик таблиц, 10.09.2026). Кадру задали ширину, и он заодно перестал
  расти по высоте. Ловушка в том, что размер задают РАНО, пока кадр пустой:
  колонка получала ширину до наполнения и навсегда оставалась 32 px высотой,
  а таблица 96 px. Лечение: помнить задуманный режим своих кадров и ставить
  его заново после каждого `resize`, а размер по одной оси задавать, не трогая
  вторую (`resize(нужное, node.height)`).
- **Проверка по размеру обманывает, если размер и так совпадал** (сборщик
  таблиц, 10.09.2026). Кадры из `createFrame` рождаются 100×100 (и
  родитель, и ребёнок), поэтому «размер ребёнка равен размеру родителя»
  выполняется ещё до записи, и первое же фигмовское имя засчитывается как
  сработавшее. Снаружи всё выглядело тянущимся (дети корня отличались от
  него размером и проверялись честно), а обёртки внутри оставались
  фиксированными. Правило: **перед записью свойства убедитесь, что размер
  ребёнка ОТЛИЧАЕТСЯ от ожидаемого**, а если совпадает, сбейте его
  `resize`-ом на несколько пикселей; ребёнок ещё не тянущийся, снимать с
  него нечего. Родное имя ставьте первым: оно и работает, и не даёт ложных
  срабатываний фигмовским. Для главной оси ожидание это остаток: размер
  родителя без отступов, соседей в потоке и зазоров.
- **Растянуть ребёнка по оси, где родитель «по содержимому» (`AUTO`), нельзя.**
  Вертикальный скроллбар и боковая панель в кадре с `counterAxisSizingMode =
  'AUTO'` остаются своей высоты. Сначала фиксируйте размер родителя по этой
  оси, потом растягивайте детей.
- **`appendChild` может не вложить слой**, и тогда он остаётся лежать на
  странице отдельным куском, а композиция рассыпается. Проверяйте
  `node.parent === parent` после вызова и пишите в журнал, что осталось снаружи.

- **`resize()` снимает и растяжение ребёнка в родителе, по обеим осям**
  (сборщик таблиц, 13.09.2026).
  Область прокрутки тянулась по ширине, потом ей «сбивали» высоту `resize`-ом,
  чтобы проверить растяжение по высоте, и ширина становилась фиксированной.
  Так ведёт себя Figma, и симптом в боевой среде совпал; отдельно на стенде это не
  измерялось. Лечение: помнить, как каждый слой должен тянуться, и после
  любого `resize` ставить растяжение заново (без проверки: она уже была).

### 7б. Размер окна плагина: `ui.resize` есть, но верить ему нельзя

`pixso.ui.resize(width, height)` и `pixso.ui.bounds` есть в типах
(`@pixso/plugin-typings` 2.0.4), значит окно можно сделать растягиваемым:
уголок в окне, `pointermove` → сообщение вниз → `ui.resize`. Тонкости:

- **менять размер умеет только песочница**: в окне `window.resizeTo` не
  работает, origin у iframe пустой. Значит на каждый шаг мыши уходит
  сообщение. Шлите не чаще кадра (`requestAnimationFrame`), между кадрами
  держите только последний размер;
- **считайте от экранных координат** (`event.screenX/Y`) и от размера на
  момент нажатия: окно меняется прямо под курсором, и «текущий размер плюс
  шаг» убегает;
- **успех проверяется по `ui.bounds` до и после**: как и с автолейаутом,
  «не бросило» не значит «применилось»;
- размер стоит запоминать в `clientStorage` **отдельным ключом** от настроек:
  он про рабочее место, а не про содержимое, и не должен ездить вместе с
  пресетами;
- **`ui.bounds` в веб-сборке это обещание**, а в типах объект (по поведению
  веб-сборки, 13.09.2026): читайте через `Promise.resolve(...)` с таймаутом,
  иначе сверка «до и после» сравнивает обещание с числом и молча проходит.
  Сверку делайте один раз, на первом вызове, а вызовы выстраивайте в
  очередь: асинхронный первый шаг иначе обгоняется вторым;
- **`ui.reposition(x, y)` есть** и работает,
  так окно тянется и за левую/верхнюю стороны: при нажатии окно просит
  `bounds`, а дальше вместе с размером шлёт `x = x0 + (w0 − w)`. Если
  `bounds` пришёл пустым (0×0), сдвигать нельзя: тянуть без сдвига.

### 8. Внутрь экземпляра `findAll` не заходит

`instance.findAll(n => n.type === 'TEXT')` возвращает пустой список, хотя
текстовые слои внутри есть. Обходите детей сами (`node.children` по очереди,
в порядке документа), а если слой всё равно не правится, пишите текст через
текстовое свойство компонента:

```js
var props = instance.componentProperties;            // { 'Title#1': { type: 'TEXT' } }
instance.setProperties({ 'Title#1': 'Договор' });
```

Порядок такой: слой → свойство компонента → честная строка в отчёте, что
подпись не встала.

### 9. Прозрачность слоя не попадает в снимок

`node.exportAsync()` рисует слой **в полную силу**, без его собственной
прозрачности. Размытие, тени и градиенты в снимок попадают, а прозрачность
нет: полупрозрачное свечение станет непрозрачным пятном. Переносите её сами.

### 10. Режим наложения и размытие фона снять по отдельности нельзя

Их цвет считается по тому, что лежит снизу. Такой слой обязан остаться в общем
снимке кадра, иначе будет выглядеть иначе, чем в макете.

### 11. Обновления библиотек: видны, но обновляются только все сразу

Разобрано по поведению веб-сборки pixso.net 12.09.2026 при работе над плагином
обновления компонентов. **На внутреннем стенде своя сборка, там не проверялось.**

- `getLibraryChange()` отдаёт те же обновления, что панель ассетов:
  компоненты, наборы и стили, у которых в библиотеке опубликована новая
  версия, а файл её ещё не принял. Сгруппировано по библиотекам:
  `{ name, key, componentList, styles }`, у наборов есть `variants` с ключами.
  В типингах вызов синхронный, **в веб-сборке асинхронный**. Принимайте оба
  вида (если `then` есть, ждать под таймаутом).
- `updateLibraryComponentAsync()`: **без аргументов** и обновляет **все**
  компоненты с обновлениями разом, как кнопка в панели ассетов. Выборочно,
  по одному, плагин обновить не может, хотя сам Pixso внутри обновляет
  по одному. Промис разрешается **раньше**, чем обновление допишется в файл
  (внутри `forEach` без ожидания). Перечитывайте файл с задержкой. Только
  режим дизайна.
- `importComponentByKeyAsync(key)` берёт **опубликованную** версию: запись из
  каталога подписанных библиотек (у неё `content_hash` и `canvas_url` текущей
  публикации), а если ключа там нет, то с сервера, и делает `upsertSharedSymbol`
  с этой версией. Заменяет ли он при этом старую копию того же компонента
  в файле или кладёт новую рядом, не проверено. (Сначала здесь было «новую
  версию не подтягивает». Это ошибка разбора: каталог удалённых компонентов
  это библиотека, а не копии файла; исправлено 13.09.2026.)
- **Вложенный атом держит свою версию в каждом шаблонном компоненте.** Один
  компонент (один `componentKey`) лежит в файле несколькими копиями разных
  версий (`sharedSymbolVersion`), и шаблонный компонент ссылается на ту,
  с которой его опубликовали. Замер на рабочем файле 13.09.2026. Button 32 XS
  из одной библиотеки: внутри одного шаблона подпись у края и отступ
  10, внутри шаблона из другой
  библиотеки по центру и 4; атомов, живущих сразу в разных версиях, 27.
  Новый атом внутри шаблона появится, только когда библиотека шаблонов примет
  обновление атома и переопубликуется. **Версию плагин не видит**: такого
  свойства у компонента нет, а `getPublishStatusAsync` отвечает только для
  компонентов самого файла (у чужих всегда `UNPUBLISHED`). Различить копии
  можно по `mainComponent.id` при одинаковом `key` и по содержимому.
- Дат публикации и описания «что поменялось» в API нет: «давно не обновляли»
  по времени плагин не узнает.

### 12. Каталог библиотеки: стили общим списком, а не как в типингах

`getLibraryByKeyAsync(fileKey)` отдаёт `{ name, key, subscribed, componentList,
styles }`, где `styles` это **общий список** `{ name, key, description,
thumbnailUrl, type }`; `type`: `PAINT`, `TEXT`, `EFFECT`, `GRID` (заливка и
обводка обе `PAINT`). В типингах 2.0.4 описан другой вид: `style: { paints,
texts, effects, grids }`; кто читает только его, получает **пустой каталог без
ошибки**. Читайте оба вида. Разобрано по поведению веб-сборки 13.10.2026, когда
замена библиотеки в одном из плагинов на стенде отвечала «заменять нечего».

Рядом: `style.getLibraryInfoAsync()` отдаёт `{ key: ключ файла библиотеки, name }`,
а если библиотеку стиля найти не удалось, **сам открытый файл**. Ключ открытого
файла: `pixso.fileKey` (в типингах нет). `getLibraryByKeyAsync` с ключом
открытого файла бросает.

### 13. `getStyledTextSegments` это заглушка

В веб-сборке метод есть, но всегда отдаёт пустой список, в типингах он
закомментирован. Стиль куска текста дают `getRangeFillStyleId(start, end)` и
`getRangeTextStyleId(start, end)`: id или `pixso.mixed`. Отрезки находятся
делением пополам, пока у куска не окажется один стиль. Запись: `setRangeFillStyleId` / `setRangeTextStyleId`.

## Режим разработки с горячей перезагрузкой

Pixso подхватывает плагин с локальной машины по фиксированному порту **5201**:
отдаёт `ui.html` по HTTP и слушает WebSocket на `/plugin`, куда сервер шлёт
JSON `{name, content}` с текстами `manifest`, `main` и обёртки `ui`.

Официальный путь это `@pixso/plugin-cli`, но протокол простой, и в
`tools/dev-server.js` он реализован без зависимостей. Оговорка: в этом режиме
окно живёт на обычном origin (`http://localhost:5201`), а у собранного плагина
origin пустой. Условия для Web API разные, поэтому скачивание файла и хранилище
надо перепроверять на собранном плагине.
