## Раскладка архива

**Первое, что надо проверять, когда опубликованный плагин не запускается.**
Подтверждено публикацией 08.09.2026: плагин, который три круга не работал на
стенде, заработал с первого раза, когда архив пересобрали правильно. Ни манифест,
ни код при этом не меняли.

Клиент скачивает пакет и ищет в нём запись с именем **ровно `manifest.json`,
в корне архива**. Следом ищет `main` и `ui` по путям из манифеста, тоже точным
совпадением строк. Папку-обёртку он не срезает, а ошибку разбора **глотает
молча**. Снаружи это карточка, которая есть, и нажатие, которое ничего не делает.

Архив, сжатый через Finder на macOS, **не работает**:

```
пакет/                     ← папка-обёртка, из-за неё всё и ломается
пакет/manifest.json
пакет/dist/main.js
__MACOSX/…  и .DS_Store    ← служебный мусор macOS
```

Рабочий архив:

```
manifest.json
dist/main.js
dist/ui.html
```

**Локальная загрузка идёт мимо архива:** приложение читает файлы с диска по
путям манифеста. Отсюда правило распознавания: **«локально работает, на
публикации нет» при одинаковом коде значит упаковку или сервер, а не плагин.**
Искать в коде и манифесте в этом случае бесполезно.

## Манифест

Манифест, проверенный запуском на внутреннем стенде 01.09.2026. С тех пор
на нём работают все опубликованные плагины, с которых собран этот скилл:

```json
{
  "id": "pptx_export",
  "name": "Экспорт в PowerPoint",
  "main": "dist/main.js",
  "ui": "dist/ui.html",
  "permissions": ["activeDocument", "currentPage", "currentSelection"],
  "editorType": ["pixso", "dev"]
}
```

| Поле | Зачем |
|---|---|
| `id` | идентификатор, snake_case |
| `name` | имя в списке плагинов и на панели |
| `main` | код песочницы |
| `ui` | разметка окна. **Поле остаётся, и файл обязан лежать в пакете**, даже когда разметка вшита в код |
| `permissions` | `activeDocument`, `currentPage`, `currentSelection`, именно эти имена |
| `editorType` | `["pixso", "dev"]`, режимы, в которых плагин виден в списке |

Ни `menu`, ни метаданных (`version`, `author`, `description`, `icon`, `type`,
`manifestVersion`, `host`) в нём нет, и без них всё работает: плагин
открывается нажатием на карточку.

### Откуда этот набор и почему его держаться

- `editorType` и `menu` описаны в [документации манифеста](https://pixso.net/developer/en/plugin-api/guide/manifest.html),
  но их нет в типах `@pixso/plugin-typings`: типы описывают API во время работы,
  а не файл настроек. Без `editorType` плагин виден только в режиме дизайна.
- `permissions` нет ни в документации, ни в типах. Набор с этими именами
  взят из манифеста плагина, который уже запускался на том же стенде.
- По поведению клиента для запуска хватает `name` и `main`. Но до 08.09.2026
  плагины не запускались на стенде из-за архива, и тогда же перебирались наборы
  полей, поэтому какой из них на самом деле был ни при чём, уже не узнать.
  Шесть полей выше проверены запуском и с тех пор ни разу не подводили.
- В открытых репозиториях встречаются другие наборы полей (`type`,
  `manifestVersion`, `host`, `permissions: ["currentDocument", "library"]`).
  Платформа, судя по всему, принимает больше одного набора. Копировать чужой
  набор не нужно, держитесь проверенного.

**Правило: манифест берётся из образца, проверенного запуском на том же стенде,
и не додумывается.** Если в манифесте всё как выше, а плагин не запускается,
виноват не он: смотрите архив.

Сборщик сверяет набор полей **на точное совпадение** и падает не только на
нехватке, но и на любом добавлении. Каждое новое поле стоит отдельного круга
публикации, а он идёт по запросу и занимает дни. Пусть добавление будет
осознанным решением, а не недосмотром. Проверка уже есть в каркасе,
`tools/make-local-build.js` и `pack.sh`.

## Официальный инструмент

У Pixso есть свой сборщик `@pixso/plugin-cli` (npm) с командами `dev`, `build`,
`pkg`. Даже если проект пишется без npm, полезно знать, что он делает: это
эталон, с которым сверяются догадки.

Упаковка (`pkg`) кладёт **`manifest.json` в корень архива, рядом папку `dist/`**.
Плоско, без внешней папки и без картинок карточки. Каркас собирает такой же.

`build` вшивает скрипт окна прямо в `dist/ui.html`. Это то же решение, что
«вшить разметку в код» ниже, только уровнем выше. Одна самодостаточная страница
это норма, а не костыль.

В облачном Pixso официальная инструкция публикует плагин из панели плагинов
загрузкой `manifest.json`. На корпоративном стенде плагин подают на проверку
архивом, и проверка занимает дни. Поэтому догадки надо отсекать до отправки.

## Три способа доставки

| Способ | Что отдаётся | Когда |
|---|---|---|
| дев-сервер | файлы по WebSocket на порт 5201 | правки в реальном времени |
| локальная загрузка | папка `local-build/` с `manifest.json` и `dist/` | проверка сборки в Pixso Desktop |
| архив | `publish/<id>.zip` из `release/` | публикация |

В дев-режиме окно живёт на настоящем origin (`http://localhost:5201`), там
работает `localStorage`. У собранного плагина origin пустой. Поэтому скачивание
файла и хранение настроек проверяются **на собранном плагине**, а не в дев-режиме.

## Сборка: окно вшивается в код

На части сборок Pixso файл из `manifest.ui` до плагина не доезжает: код
запускается, окно остаётся пустым. Обход в том, чтобы **вшить разметку прямо
в скрипт**. Поле `ui` при этом **остаётся в манифесте, а файл в пакете**: набор
полей обязан совпадать с проверенным, а лишний файл ничему не мешает.

```js
const ui = fs.readFileSync('ui.html', 'utf8');
const main = fs.readFileSync('main.js', 'utf8');
const bundled = 'var INLINE_UI = ' + JSON.stringify(ui) + ';\n' + main;
```

В `main.js` разметка берётся из вшитой строки, если она есть, и только иначе
из `__html__`:

```js
var UI_HTML = (typeof INLINE_UI === 'string' && INLINE_UI.length)
  ? INLINE_UI
  : ((typeof __html__ === 'string') ? __html__ : '');
```

Готовый сборщик `tools/make-local-build.js` есть в каркасе. Он собирает две
одинаковые папки:

- `local-build/` для загрузки в Pixso Desktop на своей машине, в git не кладут;
- `release/` для репозитория. На стенд, где нет терминала, плагин берут готовым
  из репозитория, поэтому `release/` пересобирают перед каждым коммитом.

У манифестов две роли. Корневой загружают прямо из папки плагина, он ссылается
на `main.js` и `ui.html` рядом с собой. Манифест в пакете ссылается на `dist/`.
Пути проставляет сборка и проверяет, что файлы по ним есть: если манифест
ссылается на файл, которого нет, Pixso молча не запускает плагин.

Перед сборкой выключите дев-зонд (`DEV_PROBE = false`), если добавляли его,
иначе собранное окно будет стучаться на локальный сервер, которого нет.

## Архив для публикации

```bash
./pack.sh        # сборка, обе проверки, publish/<id>.zip из release/
```

**Собирать архив только скриптом, никогда не через Finder** («Сжать»
в контекстном меню): он добавит папку-обёртку и `__MACOSX`, и плагин не
запустится, см. «Раскладка архива».

`pack.sh` в конце читает готовый архив так же, как его читает Pixso. Проверка
дешёвая и ловит именно ту ошибку, которая стоила трёх кругов публикации:

```python
import sys, zipfile, json
names = zipfile.ZipFile(sys.argv[1]).namelist()
if names[0] != 'manifest.json':
    sys.exit('Первой записью обязан идти manifest.json, а идёт ' + names[0])
junk = [n for n in names if '__MACOSX' in n or n.endswith('.DS_Store')]
if junk:
    sys.exit('В архиве мусор macOS: ' + ', '.join(junk))
man = json.loads(zipfile.ZipFile(sys.argv[1]).read('manifest.json'))
for field in ('main', 'ui'):
    want = man.get(field)
    if not want:
        continue
    # Клиент допускает ведущее ./, сверяемся ровно так же, как он
    if want not in names and want.lstrip('.').lstrip('/') not in names:
        sys.exit('Манифест ссылается на ' + want + ', а такой записи нет')
print('Архив читается так же, как его читает Pixso: ' + ', '.join(names))
```

Проверить руками: `unzip -l publish/<id>.zip | head`, первой записью должен
идти `manifest.json`.

## Материалы карточки

| Что | Требование |
|---|---|
| пакет | `publish/<id>.zip`, обязан распаковываться |
| обложка | 1600 × 900 |
| иконка | 128 × 128 |
| описание | текст, который видно при запуске плагина |

Описание пишется для пользователя, а не для разработчика. Что работает: первая
строка про то, что получится («каждый выбранный фрейм становится отдельным
слайдом»), дальше список «что умеет», каждый пункт коротким утверждением
с пояснением. Обезличенно, без жирных ярлыков в начале пунктов и без обещаний,
которых плагин не выполняет. Если тень с разлётом уходит картинкой, так и
напишите, иначе первое же расхождение подорвёт доверие ко всему остальному.

Держите текст карточки в файле репозитория (например `ОПИСАНИЕ.md`) вместе
с требованиями к картинкам: он переписывается чаще, чем кажется.

## Что проверить перед выдачей

- плагин запускается **нажатием на карточку** и открывает окно, пункт меню для
  этого не нужен;
- список узлов приходит и обновляется при смене выделения;
- основная кнопка работает, то есть канал из окна в плагин поднялся;
- настройки переживают перезапуск (`clientStorage`);
- файл скачивается сам, а если среда запретила, выручает видимая кнопка;
- пустое состояние и состояние ошибки выглядят как задумано;
- журнал объясняет каждый случай приблизительного переноса;
- **архив собран скриптом**, и `unzip -l` показывает `manifest.json` первой
  записью;
- `release/` пересобран и закоммичен вместе с кодом, README обновлён.
